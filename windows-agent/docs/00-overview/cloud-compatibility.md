# Compatibilidad con Jarvis Cloud

Fuente de verdad del transporte: la documentación de Jarvis Cloud en [`api/docs`](../../../api/docs/README.md), en particular [MQTT Protocol v1](../../../api/docs/03-protocols/mqtt-protocol.md), [Task State Machine](../../../api/docs/02-domain/task-state-machine.md), [Error Model](../../../api/docs/03-protocols/error-model.md) y [Windows Agent Contract](../../../api/docs/07-integrations/windows-agent-contract.md). Este proyecto **no redefine** el protocolo: donde el pedido original o una necesidad del agente difiere, se documenta aquí.

Resumen: **ninguna incompatibilidad bloquea el MVP.** Las diferencias se resuelven adaptando el agente al contrato del Cloud o con extensiones **aditivas** (campos opcionales que el Cloud hoy ignora, permitidas por la regla de versionado del protocolo). Las que requieren cambios en el Cloud están marcadas como tales.

| # | Issue | Definición del Cloud | Requisito / propuesta del Windows Agent | Resolución recomendada | Documentos afectados |

## Comprobado contra el Cloud real (2026-09-19)

Lo que se vio al ejecutar [WIN-E2E-01…14](../11-testing/integration-scenarios.md) contra la API y el broker reales. Nada de esto rompe el contrato: son diferencias de vocabulario y de comportamiento del broker que conviene tener escritas.

| Observación | Detalle | Efecto en el agente |
|---|---|---|
| El Cloud no tiene estado `Rejected` | `task.rejected` se aplica como `Failed` conservando el `error.code` del agente | Ninguno: el agente sigue distinguiendo rechazo (antes de ejecutar) de fallo (durante la ejecución) en sus propios mensajes y en la base local |
| Una firma inválida se ve como `NOT_PERMITTED` | Por C5, un rechazo usa el catálogo cerrado del Cloud; el código específico va en el mensaje (`"SIGNATURE_INVALID: the signature does not match the message"`) | Ninguno, pero conviene saberlo al leer una tarea rechazada: el motivo exacto está en `error.message`, no en `error.code` |
| Tipos no declarados | `POST /api/v1/tasks` responde **422** para un tipo que el device no anuncia en `supportedTaskTypes` | El rechazo ocurre antes de llegar al agente; `UNSUPPORTED_TASK_TYPE` sigue cubriendo el caso de una tool deshabilitada entre el hello y el dispatch |
| Rotar la credencial | El broker expulsa al cliente conectado y rechaza la credencial anterior | El agente clasifica el rechazo como `AUTH_REJECTED` y vuelve solo tras `provision` + `reconnect`, sin reiniciarse |
| Ráfaga de duplicados | 100 `task.dispatch` idénticos publicados como el Cloud | Una sola ejecución; el limitador de entrada (50 msg/s) descarta el exceso y lo registra agregado |
